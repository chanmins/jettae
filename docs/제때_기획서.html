01

서비스 개요

한 줄 정의

제때는 집 안 소모품의 교체 시기를 대신 기억해주는 앱이다. 사용자는 목록에서 탭 한 번으로 등록하고, 때가 되면 알림을 받고, 바꿨으면 탭 한 번으로 답한다. 그게 전부다.

범위 결정 (v1.0). 정수기 · 공기청정기 · 에어컨 필터류와 차량은 제외한다 — 필터야 · SmartThings · 제조사 앱이 이미 차지한 영역이고, 정작 아무도 챙기지 않는 칫솔 · 수세미 · 행주 쪽에 집중하는 편이 낫다. 필터가 빠지면서 라벨 촬영과 AI도 함께 빠졌고, 그 결과 운영비가 완전히 0이 되고 Phase 1이 몇 주 짧아졌다.

세 가지 문제

문제 1

아무도 세지 않는다

칫솔 3개월, 수세미 한 달, 렌즈 케이스 3개월. 다들 알지만 아무도 세지 않는다. 기억해야 할 물건이 스무 개쯤 되면 애초에 불가능하다.

문제 2

주기를 정확히 모른다

수세미를 얼마마다 바꿔야 하는지 정확히 아는 사람은 드물다. 검색해서 직접 넣으라고 하면 스무 개를 등록할 사람은 없다.

문제 3

기존 앱은 냉장고에 갇혀 있다

유통기한 앱은 식품만 본다. 필터·수세미·렌즈처럼 집 전체에 흩어진 소모품을 한 곳에서 보는 앱은 드물다.

해결 방식

문제제때의 답구체적 장치
세지 않는다앱이 먼저 부른다사용자가 앱을 열 이유가 필요 없다. 등록 한 번이면 이후는 알림이 끌고 간다
주기를 모른다이미 알고 있다프리셋 카탈로그 159종. 권장 주기가 들어 있어 고르기만 하면 끝. 경쟁 앱이 공통으로 놓친 지점
등록이 귀찮다탭 한 번, 2초구역을 고르면 그 공간의 물건만 보여준다. 온보딩에서 5개를 한 번에 담는다
주기가 사람마다 다르다쓸수록 맞춰진다알림에 답할 때마다 기준일이 재설정되고, 반복되면 그 사람의 실제 주기로 조정된다
운영비 부담AI를 쓰지 않는다카탈로그와 날짜 계산만으로 동작한다. 100명이든 1,000명이든 무료 티어 안, 월 $0

타깃 사용자

  • 1차 — 자취 2~3년차. 집안일을 스스로 관리하기 시작했고, 챙길 게 늘었다는 걸 체감하는 시점.
  • 2차 — 신혼·맞벌이 가구. 관리 대상이 늘고 “누가 언제 바꿨는지”를 서로 모른다.
  • 3차 (확장) — 차량·주택 설비까지 관리하는 사용자. 엔진오일, 와이퍼, 보일러, 소화기.

이미 시도된 시장

이 자리는 비어 있지만, 아무도 와본 적 없는 자리는 아니다. 비슷한 시도가 여러 번 있었고 전부 자리를 잡지 못했다. 경쟁사 목록보다 이 사실이 중요하다.

해석 — 수요가 없는가, 실행이 나빴는가

필터야가 2년 넘게 방치된 것은 개발자가 포기했다는 뜻이고, 가볍게 볼 신호가 아니다. 다만 경쟁자들이 공통으로 놓친 지점이 뚜렷하다는 점에서 후자일 가능성이 크다.

  • 프리셋 카탈로그가 없다 — 사용자가 주기를 직접 입력해야 한다. 그러면 휴대폰 리마인더와 다를 게 없고, 20개를 손으로 넣을 사람은 없다.
  • 밀렸을 때의 출구가 없다 — 붉은 항목이 쌓이면 사용자는 만회할 수 없다고 느끼고 앱을 지운다. “오늘부터 다시”를 주는 앱이 없다.
  • 단일 카테고리에 갇혀 있다 — 필터만, 정수기만. 집 전체를 보는 것은 교체알리미 정도인데 거기엔 카탈로그가 없다. 제때는 그 반대 조합이다 — 집 전체 + 카탈로그.

이 셋이 제때가 서는 자리다. 다만 교체알리미의 다운로드 50+는 신생 앱이어서일 수도 있어 실패의 증거로 단정할 수 없다. 그래서 만들기 전에 수요부터 확인한다 — 7장 Phase -1.

이 앱이 하지 않는 것

비목표(Non-goals). ① 가계부가 아니다 — 지출을 기록하지 않는다. ② 쇼핑몰이 아니다 — 직접 팔지 않는다. ③ 청소·습관 트래커가 아니다 — 매일 체크할 것을 늘리지 않는다. ④ IoT 연동은 MVP 범위 밖이다.

02

핵심 컨셉

네 단계 루프

1
등록한다 — 딱 한 번

목록에서 고르거나(2초), 라벨을 찍는다(10초). 이후 이 물건을 위해 사용자가 할 일은 없다.

2
앱이 센다 — 사용자는 잊는다

사용자가 앱을 열지 않아도 된다. 잊는 게 정상이고, 잊어도 되게 만드는 것이 이 앱의 가치다.

3
때가 되면 부른다

“오늘 바꿀 것 3개”. 하루 한 번, 여러 품목을 묶어서. 잠금화면에서 바로 처리할 수 있어 앱을 열 필요가 없다.

4
답하면 맞춰진다 — 탭 한 번

“바꿨어요”를 누르면 그날이 새 기준일이 된다. 첫 등록이 부정확해도 한 주기면 정확해진다.

설계 원칙 셋

원칙 1

의지에 기대지 않는다

습관 앱은 사용자가 매일 앱을 열어야 한다. 제때는 반대다. 앱이 먼저 부른다. 이것이 리텐션 구조의 전부다.

원칙 2

날짜는 나중, 사실은 지금

기준일은 틀려도 된다 — 알림 응답이 재설정해준다. 하지만 모델명 · 규격 · 유통기한은 저절로 고쳐지지 않으므로 등록 시점에 반드시 확인받는다.

원칙 3

막지 않고 되돌린다

이 앱의 사용자는 물건을 미룬 사람이다. 밀린 게 12개여도 화면은 담담해야 하고, 언제든 오늘부터 다시 시작할 출구가 있어야 한다.

비슷해 보이는 것들과의 차이

대안한계제때의 차이
휴대폰 캘린더 · 리마인더주기를 직접 알아내서 직접 입력해야 한다. 20개를 등록할 사람은 없다프리셋 카탈로그가 주기를 이미 알고 있다
유통기한 관리 앱식품 중심. 필터·수세미·렌즈는 대상 밖집 전체 소모품이 대상
메모장 · 스프레드시트먼저 열어봐야 안다. 결국 안 연다알림이 먼저 온다
제조사 앱 · SmartThings그 브랜드 가전만. 칫솔·수세미·렌즈 케이스는 대상 밖가전이 아닌 것들이 대상
03

등록 설계

등록은 이 앱의 유일한 진입 마찰이다. 여기서 막히면 나머지 설계가 전부 무의미하므로, 품목의 성격에 따라 세 갈래로 나눈다.

두 갈래

갈래해당 품목사용자 동작카탈로그
① 목록 선택칫솔, 수세미, 행주, 면도날, 침구 세탁, 렌즈 케이스, 세탁조 청소 …탭 1회 (2초)127종
② 개봉일 기준선크림, 마스카라, 영양제, 참기름, 렌즈 세척액 …탭 2회 (5초)32종

카메라는 쓰지 않는다. 초기 설계에는 라벨 촬영 갈래가 있었으나, 필터류를 제외하면서 남는 촬영 대상이 화장품 개봉기한 정도가 됐다. 그건 “오늘 개봉” + “12개월” 두 번 탭이면 끝나 사진보다 빠르다. 청소기 먼지봉투 규격 하나 때문에 카메라 · 이미지 압축 · 스토리지 · AI 파이프라인 · 인식 확인 화면을 전부 만들 이유가 없다.

② 개봉일 기준 품목

화장품 · 영양제 · 개봉한 식품은 산 날이 아니라 개봉한 날부터 세야 한다. 그리고 사용기한이 제품마다 다르다 — 마스카라는 4개월, 선크림은 12개월, 향수는 3년.

// 선크림 등록 — 탭 두 번
언제 개봉하셨어요?
  [ 오늘 개봉했어요 ]   [ 한 달쯤 전 ]   [ 세 달쯤 전 ]   [ 직접 고르기 ]

사용기한
  [ 6개월 ]   [ 12개월 ]   [ 24개월 ]      ← 카탈로그 기본값이 선택돼 있다
  제품 뒤 6M · 12M 표시를 보고 골라주세요
  • 카탈로그가 기본값을 이미 알고 있으므로 두 번째 탭은 대부분 확인만 하고 넘어간다
  • 제품 뒷면의 6M · 12M(개봉 후 사용기한) 표시를 안내한다. 그런 표시가 있다는 것조차 모르는 사람이 많다
  • 기한이 민감한 품목(영양제 · 유산균 · 렌즈 세척액)은 제조사 표기가 카탈로그 값보다 우선임을 화면에 명시한다

기준일 처리

기본값은 등록일 = 오늘이다. 다만 앱을 처음 설치했을 때 등록하는 것들은 대부분 이미 쓰고 있던 물건이라, 전부 오늘부터 세면 첫 주기가 통째로 어긋난다.

// 등록 직후 화면
🪥 칫솔          ✓ 등록됨 · 3개월 뒤 알림
                 쓰던 거예요 →   ← 안 누르면 오늘 기준, 마찰 0

// '쓰던 거예요'를 눌렀을 때만 뜨는 선택지
   대략 얼마나 쓰셨어요?
   [ 1주 ] [ 1개월 ] [ 3개월 ] [ 기억 안 남 ]

기억이 안 나면 오늘부터 세면 된다. 한 주기만 지나면 알림 응답으로 자동 교정되므로, 첫 등록의 정확도에 매달릴 필요가 없다.

프리셋 카탈로그 — 이 앱의 진짜 자산

등록이 2초가 되려면 “품목 → 권장 주기” 데이터가 이미 있어야 한다. 이 카탈로그의 품질이 곧 제품의 품질이다. 159종을 작성 완료했다(별도 파일: 스프레드시트 + JSON 시드). 아래는 발췌.

날짜로 셀 수 없는 품목 — 사용량 기준

엔진오일은 보통 7,000~10,000km에서 갈고 기간은 보조 기준이다. 정확히는 둘 중 먼저 도달하는 쪽이 교체 시점이다 — 타지 않아도 1년이 넘으면 변질되기 때문이다. 렌즈(착용 횟수)와 면도날(사용 횟수)도 같은 구조다.

사용량을 매번 입력하게 하면 아무도 쓰지 않는다. 그래서 가끔 물어서 속도를 추정한다 — 주기 자기교정과 같은 원리다.

   ↓

   ↓
알림 때    "지금 몇 km예요?" → 실제값으로 주행 속도 보정
   ↓
다음 예측이 정확해진다

카탈로그에 metric(time / usage), cycle_usage, unit을 둔다. 차량은 Phase 4지만 스키마는 지금 잡아둔다 — 나중에 필드를 끼워 넣는 마이그레이션 비용이 더 크다.

카탈로그가 해자(垓字)가 된다. 초기값은 수동 큐레이션으로 만들지만, 사용자들의 “실제로 바꾼 시점” 응답이 쌓이면 현실의 주기를 알게 된다. 사용자가 1,000명이 되면 이 데이터는 어떤 경쟁자도 하루아침에 복제할 수 없다.

예외 상황 처리

등록으로 끝나지 않는 상황이 있다. 아래 셋을 MVP에서 처리하지 않으면, 앱이 틀린 정보를 자신 있게 알려주는 상태가 된다. 알림이 안 오는 것보다 나쁘다.

① 계절 품목 — 겨울에 오는 “선풍기 청소할 때예요”

12월에 이 알림이 뜨는 순간 신뢰가 끝난다. 한국은 계절이 뚜렷해 해당 품목이 적지 않다 — 선풍기 · 제습제(여름), 가습기 · 전기장판 · 찜질팩(겨울).

  • 카탈로그에 season 필드를 둔다 — all / summer / winter
  • 시즌 밖에서는 카운트를 멈춘다. 남은 일수가 줄지 않고 얼어붙는다
  • 시즌이 시작되면 한 번만 묻는다 — “선풍기 꺼내셨어요?” 누른 날이 기준일이 된다

계절 품목은 달력이 아니라 ‘쓰기 시작한 날’이 기준이다. 시간이 아니라 사용 개시가 주기를 연다.

② 같은 품목이 여러 개 — 화장실 둘, 칫솔 넷

  • 등록 시 이미 구역을 고르므로 “욕실 칫솔”, “안방 칫솔”로 자연스럽게 갈린다. 같은 구역에 재등록하면 뒤에 번호를 붙인다
  • 가족 칫솔처럼 함께 바꾸는 것은 하나로 묶고 개수만 기록한다(group_count). 따로 관리하려는 사람만 분리한다

③ 제품 교체와 이사 — 사진과 모델명이 통째로 거짓이 되는 순간

이사하면 챙기던 물건의 절반이 바뀐다. 두고 온 것에 계속 알림이 가고, 새로 생긴 것은 아무도 세지 않는다. 목록이 현실과 어긋나는 순간 앱을 믿지 않게 된다.

  • 상세 화면에 “새것으로 바꿨어요” — 교체 이력을 새로 시작하고 주기를 카탈로그 기본값으로 되돌린다
  • 이사는 설정의 별도 흐름 — 전체 목록을 체크박스로 펼쳐 “가져온 것 / 두고 온 것”을 한 번에 정리한다
  • 이사는 오히려 재참여 기회다. 어차피 그때 집 안 물건을 전부 만지기 때문이다

이 예외들을 관통하는 뿌리가 하나 있다. 소모품은 시간이 아니라 사용량으로 닳는다. 날짜로 세는 것은 “매일 비슷하게 쓴다”는 가정 위의 근사치다. MVP는 그 근사로 가되, 근사가 깨지는 세 지점 — 계절 · 장기 부재 · 사용 빈도 — 을 알고 설계한다. 계절만 MVP에서 막고, 나머지 둘은 “쓰기 시작했어요 / 다시 셀게요” 같은 수동 리셋으로 열어둔다.

04

알림과 자기교정

이 앱은 알림이 곧 제품이다. 알림이 안 오면 존재하지 않는 앱이고, 너무 오면 삭제당한다.

알림 시점

시점내용대상
D-7미리 알림. 사러 갈 시간을 준다주기 1개월 이상 품목만
D-DAY교체 알림 + 사진 + 모델명 + 응답 버튼전체
D+3미응답 시 1회 재알림전체
D+10마지막 재알림 후 ‘밀림’ 상태로 전환전체

하루 한 번, 묶어서 보낸다. 같은 날 여러 품목이 걸리면 알림 하나로 합친다 — “오늘 바꿀 것 3개”. 발송 시간은 사용자가 정하고, 기본값은 저녁 8시(집에 있고 바로 처리 가능한 시간)로 둔다.

알림 응답

제때·오후 8:00
오늘 바꿀 것 3개
수세미, 행주, 침구 세탁
  • 바꿨어요 — 오늘이 새 기준일이 된다. 다음 알림은 오늘 + 주기.
  • 아직이요 — 3일 뒤 다시 묻는다. 기준일은 그대로 유지.
  • 아직 멀쩡해요 — 미룬 게 아니라 아직 쓸 만한 경우. 다음 절에서 따로 다룬다.
  • 앱을 열지 않고 알림에서 바로 처리할 수 있어야 한다. 이 앱에서는 앱을 열어야만 하는 것이 실패다.

알림 없이 먼저 바꾸는 경우

설계상 순서는 “알림 → 교체 → 응답”이지만, 현실에서는 자주 뒤집힌다. 마트에서 수세미가 눈에 띄어 사 오고 그냥 바꾼다. 알림은 관여하지 않는다. 앱이 이를 모르면 다음 주에 “수세미 바꿀 때예요”가 뜨고 사용자는 “아까 바꿨는데?”라고 생각한다. 반복되면 앱을 믿지 않게 된다.

1
홈 맨 위 빠른 기록 — 주력 경로

임박 순 3개를 칩으로 띄운다. 탭 한 번이면 오늘로 기록되고 끝난다. 목록보다 위에 둔다. 사용자가 스스로 앱을 연 순간은 실패가 아니라 기회다 — 2초 안에 끝나기만 하면 된다.

2
알림에서 소급

알림의 “바꿨어요”는 그냥 오늘로 기록한다. 며칠 오차는 소모품 주기에서 의미가 없다. 한참 전에 바꾼 경우만 상세 화면에서 마지막 교체일을 직접 고친다.

3
자기교정이 따라온다

미리 바꾸는 것이 습관이면 실제 주기가 드러난다. 주기가 한 번 조정되면 ‘미리 바꾸는 일’ 자체가 사라진다. 알림이 그 사람의 리듬에 맞아버리기 때문이다.

이 문제는 저절로 작아진다. 자주 미리 바꾸게 되는 품목(수세미 · 행주 · 청소포)은 애초에 며칠 오차가 무의미하고, 오차가 신경 쓰이는 긴 주기 품목(베개 · 매트리스 · 화재감지기)은 알림 없이 자발적으로 바꾸는 일이 거의 없다. 이 비대칭이 문제를 줄여주므로 과하게 설계하지 않는다. 그리고 앱이 틀려도 응답 한 번이면 복구된다.

“아직 멀쩡해요” — 늦게 바꾸는 쪽의 교정

수세미를 등록했는데 요리를 자주 안 해서 한 달이 지나도 거의 새것일 수 있다. 이때 사용자는 미룬 게 아니라 아직 쓸 만한 것이다. “아직이요”로 받으면 사흘 뒤에 또 물어보게 되어 잔소리가 된다.

카탈로그의 30일은 매일 설거지하는 집 기준이다. 사용 빈도가 낮으면 안 맞는 게 정상이고, 이건 오류가 아니라 개인차다. 그래서 세 번째 응답을 둔다.

응답의미앱의 처리
바꿨어요교체 완료오늘이 새 기준일. 이력에 기록
아직이요미뤘다3일 뒤 재알림. 기준일 유지
아직 멀쩡해요덜 닳았다주기의 30%만큼 미룬다(30일 → +9일). 반복되면 주기 자체를 늘릴지 제안

두 번째 물음은 질문을 바꾼다. 푸시 액션 버튼은 두 개까지가 현실적이므로, D-DAY 알림은 [바꿨어요] [아직이요]로 두고 D+3 재알림에서 “수세미, 아직 멀쩡한가요?” → [멀쩡해요] [곧 바꿀게요]로 묻는다. 화면 안에서는 처음부터 세 선택지를 모두 노출한다.

안전 품목은 예외다. 화재감지기 건전지 · 소화기 · 가스 호스는 “아직 멀쩡해요”로도 주기가 늘어나지 않는다(safety_locked). 미룰 수는 있어도 권장 주기는 그대로 유지한다.

주기 자기교정

사람마다 실제 주기는 다르다. 칫솔을 3개월로 잡아뒀지만 매번 4개월 반에 바꾸는 사람이 있다. 응답 이력이 쌓이면 그 사람에게 맞춘다.

// 교정 로직
if (응답 이력 >= 3회) {
  실제주기 = 중앙값(최근 3회의 교체 간격)   // 평균 대신 중앙값 — 이상치 방어

  if (|실제주기 - 현재주기| > 현재주기 * 0.3) {
    // 양방향 — 일찍 바꾸는 사람도, 늦게 바꾸는 사람도 같은 로직
    // 30% 이상 차이 나면 제안한다. 몰래 바꾸지 않는다
    제안("칫솔을 보통 4개월 반에 바꾸시네요. 주기를 바꿔드릴까요?")
  }

  // '아직 멀쩡해요'가 3회 누적돼도 같은 제안을 띄운다
}

임의로 바꾸지 않고 제안한다. 사용자 모르게 주기가 달라지면 앱을 신뢰할 수 없게 된다. 안전 관련 품목(화재감지기 배터리, 소화기)은 자기교정 대상에서 제외하고 권장 주기를 고수한다.

알림 피로 방지

  • 묶음 발송 — 하루 최대 1건. 여러 품목은 하나로 합친다.
  • 연속 무시 감지 — 같은 품목을 3회 연속 무시하면 “이건 계속 알려드릴까요?”로 한 번 묻고, 아니면 조용히 보관 처리한다.
  • 짧은 주기 상한 — 2주 미만 주기 품목은 등록 시 “자주 알림이 갑니다”를 고지한다.
  • 휴면 모드 — 장기 부재(여행 등) 시 전체 알림을 일시 정지. 복귀 시 “안 쓴 만큼 미룰까요?”를 한 번 묻는다.

밀린 항목이 쌓였을 때

한 달 만에 앱을 열었더니 붉은 항목이 15개. 이 화면을 보면 사용자는 만회할 수 없다고 느끼고 앱을 지운다. 밀린 항목은 목록 그대로 보여주면 안 된다.

  • 밀린 것이 5개를 넘으면 목록을 접고 배너 하나로 요약한다 — “밀린 것 12개”
  • 탭하면 일괄 처리 화면. 가장 큰 버튼은 “지금부터 다시 셀게요” — 과거를 캐묻지 않고 전부 오늘 기준으로 리셋한다
  • 개별로 “바꿨어요 / 이제 안 써요”도 고를 수 있게 하되, 기본 출구는 일괄 리셋이다. 자비로운 탈출구가 없으면 이탈한다

조용한 실패 — 푸시가 죽은 경우

방해금지, 폰 교체, 권한 해제, iOS에서 홈 화면 앱 삭제. 서버는 발송 성공으로 기록하지만 사용자에게는 닿지 않는다. 아무도 에러를 보지 못한다. 알림이 곧 제품인 앱에서 가장 위험한 실패 방식이다.

  • 사용자별 알림 응답률을 감시한다. 3회 연속 무응답이면 푸시가 죽은 것으로 간주
  • 이메일로 1회 폴백 — “알림이 안 가고 있는 것 같아요” + 재설정 링크
  • 재구독에 실패한 기기는 push_subscriptions에서 정리한다

등록 플로우

1
중앙 + 버튼 → 품목 목록

구역별로 묶인 프리셋 159종. 진입점은 여기 하나다.

2
품목 선택

① 갈래(칫솔 · 수세미 등 127종)는 여기서 끝난다. 탭하면 담기고 “3개월 뒤 알림”이 뜬다. 연속으로 여러 개 담을 수 있다.

3
개봉일 · 사용기한 — ② 갈래 32종만

“오늘 개봉했어요”와 사용기한 버튼. 카탈로그 기본값이 이미 선택돼 있어 확인만 하면 된다.

4
기준일 확인 (선택)

기본은 오늘. “쓰던 거예요”를 누른 사람만 대략적인 시점을 고른다.

와이어프레임은 별도 문서로 작성했다. 온보딩 5화면과 홈 · 추가 · 상세 · 알림 · 밀린 항목 · 계절 재개 · 알림 꺼짐 화면, 그리고 알림 · 빈 상태 · 에러 문구가 확정 카피로 들어가 있다.

온보딩 — 5개와 2주가 관건

온보딩에 통과 조건은 없다. 하나도 고르지 않고 끝까지 넘어갈 수 있다. 체크박스를 채워야 다음으로 갈 수 있는 온보딩은 가짜 활성화를 만든다 — 관문을 넘으려고 아무거나 체크한 사용자는 진짜 사용자가 아니고, 첫 알림이 왔을 때 자기가 뭘 등록했는지도 모른다.

대신 빈손으로 나간 사용자를 홈에서 다시 만난다. 등록이 0개면 홈이 곧 추천 화면이 되고, 강요가 아니라 두 번째 기회가 된다. 다만 알아둘 것은 — 등록 0개인 사용자에게는 알림을 보낼 방법이 없다. 그 사람과의 유일한 접점은 빈 홈 화면 하나뿐이므로, 이 화면이 온보딩의 마지막 페이지만큼 공들여 설계돼야 한다.

  1. 가치 제안 2장 — “바꿀 때를 대신 세어드려요” / “바꿀 땐 뭘 살지도 알려드려요”
  2. 집 구역 선택 — 욕실 / 주방 / 거실 / 침실 (해당하는 곳만)
  3. 추천 목록 제시 — 선택한 구역의 흔한 품목을 체크박스로. 짧은 주기 품목이 위에 오고 기본 체크되어 있지만 언제든 해제할 수 있고, 전부 해제하고 넘어가도 막지 않는다(버튼 문구가 “5개로 시작하기” → “건너뛰기”로 바뀔 뿐)
  4. 목록 아래에 두 개의 출구 — “다른 것 찾아보기”(카탈로그 159종 전체)와 “직접 추가하기”(목록에 없는 것). 추천만 강요하지 않는다
  5. 홈 화면 추가 안내 — 만들지 않는다. PWA를 배포하지 않기로 했으므로 이 화면은 존재 이유가 사라졌다. 온보딩은 4단계다
  6. 알림 시간 설정 — 기본 저녁 8시. 등록이 0개여도 이 화면은 그대로 진행한다. 설정을 미리 받아두면 나중에 다시 물을 일이 없다

시간 설정과 OS 권한 요청을 분리한다. 온보딩의 “언제 알려드릴까요?”는 앱 안의 설정일 뿐이고, 실제 시스템 알림 권한 팝업은 첫 등록 직후에 띄운다. 등록이 0개인 상태에서 권한을 요구하면 — 알릴 것도 없는데 — 거절률이 올라가고, iOS는 한 번 거절하면 설정 앱까지 들어가야 해서 회복이 어렵다. “이제 알림이 갈 일이 생겼다”는 맥락에서 물어야 승낙률이 높다.

강요하지 않는다. 추천 목록은 출발점이지 정답이 아니다. 사용자가 3개만 고르고 넘어가려 해도 막지 않는다 — 짧은 주기 품목이 하나도 없을 때만 한 번 권하고, 그래도 넘어가면 그대로 보낸다. 억지로 5개를 채운 사용자보다 첫 알림을 좋게 겪고 스스로 추가한 사용자가 훨씬 오래 남는다. 추가 유도는 온보딩이 아니라 첫 알림 이후에 한다.

// 매일 5분 간격 배치 — 사용자별 알림 시각에 맞춰 발송
SELECT u.id, array_agg(i.id)
FROM items i JOIN user_settings u ON ...
WHERE i.next_due <= today
  AND i.status = 'active'
  AND u.notify_at = current_slot        // 사용자가 정한 시각
  AND (u.dormant_until IS NULL OR u.dormant_until < today)
GROUP BY u.id                            // ← 사용자당 1건으로 묶음

PWA에서 네이티브로

  • 레이어 분리 — core/(주기 계산 · 자기교정 · 계절 판단 · 카탈로그)를 부수효과 없는 순수 함수로 짠다. Swift · Kotlin으로 이식할 것이므로 그대로 옮겨지지는 않지만, 테스트 케이스가 그대로 이식 명세가 된다. 같은 입력에 같은 출력이 나오면 이식이 끝난 것이다.
  • Capacitor 단계는 건너뛴다 — PWA를 배포하지 않으므로 중간 래핑의 이득이 없다. PWA는 로직과 화면 흐름을 빠르게 검증하는 도구이고, 배포본은 처음부터 네이티브로 만든다.
  • 네이티브에서만 되는 것 — 홈 위젯(오늘 바꿀 것), 잠금화면 알림 액션, 정확한 예약 알림, 바코드 스캔.

수익 모델 후보

  • 재구매 제휴 (Phase 3~) — 알림을 받은 사용자는 이미 “사야 하는 상태”라 전환율이 높다. 품목명 기반 검색 연결부터 시작하면 되고, 앱 경험을 해치지 않는 가장 자연스러운 경로다.
  • 무료 한도 + 구독 — 무료 20개 품목, 이상은 월 구독. 다만 등록을 늘려야 하는 앱에서 등록에 한도를 거는 건 자기모순이라 신중해야 한다.
  • 완전 무료 유지 — 100명 규모에서 월 $0~2라 개인 프로젝트로는 부담이 없다. 수익화는 사용자가 생긴 뒤에 결정해도 된다.
